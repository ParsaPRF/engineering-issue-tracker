# سناریوی دمو (۱۰ تا ۱۲ دقیقه)

این سند دقیقاً می‌گوید در جلسه چه کاری به‌ترتیب انجام بدهی، چه چیزی بگویی، و اگر چیزی خراب شد چه
کار کنی. هدف: ۳ نمره‌ی «کد نویسی و صحت عملکرد» را با **نشان دادن سیستم واقعی** بگیری، نه با اسلاید.

---

## ۰. نیم ساعت قبل از جلسه (چک‌لیست)

```powershell
cd eng-tracker
powershell -ExecutionPolicy Bypass -File scripts\demo_up.ps1 -Reseed
```

این اسکریپت خودش: daemon داکر را (اگر خاموش باشد) بالا می‌آورد، **یک پورت آزاد** انتخاب می‌کند
(پورت ۸۰۸۰ روی این سیستم توسط برنامه‌ی دیگری اشغال است!)، استک را build و start می‌کند، migrate و
seed می‌زند و آدرس نهایی را چاپ می‌کند. حدود ۳ تا ۵ دقیقه طول می‌کشد.

بعد از آن حتماً این‌ها را چک کن:

| چک | دستور / کار | انتظار |
| --- | --- | --- |
| سلامت سرویس‌ها | `docker compose ps` | backend/db/redis/objectstorage/worker/web = healthy |
| ورود | مرورگر → `http://localhost:<PORT>` → `manager@example.com` / `Demo!Passw0rd` | داشبورد با ۶ بلیت |
| تب‌های آماده | ۳ تب: (۱) اپ، (۲) `.../api/docs/`، (۳) ترمینال در پوشه‌ی پروژه | — |
| فونت ترمینال | بزرگ کن (Ctrl+Scroll) | خروجی‌ها از آخر کلاس خوانده شود |
| اینترنت | برای دمو **لازم نیست** (همه‌چیز local است) | — |

**نقشه‌ی ب**: اگر داکر روی سیستمِ جلسه بالا نیامد:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\demo_up.ps1 -LocalOnly
```

این حالت بدون داکر، Django + Vite را با SQLite بالا می‌آورد (اپ روی `http://localhost:5173`).
همان قابلیت‌ها کار می‌کند؛ فقط PostgreSQL/Redis/S3 واقعی نیستند. اگر این هم نشد، مستندات + Swagger +
تست‌ها را نشان بده (بخش ۷).

## ۱. شروع: مسئله و راه‌حل (۱ دقیقه)

> «یک تیم مهندسی چند پروژه دارد، باگ‌ها و درخواست‌ها از جاهای مختلف می‌آید، و هیچ‌کس نمی‌داند چه
> کسی روی چه چیزی کار می‌کند یا چرا یک بلیت بسته شد. این سیستم یک نقطه‌ی مرکزی است برای ثبت،
> تخصیص، چرخه‌ی وضعیت کنترل‌شده، همکاری، اعلان و ردگیری فعالیت.»

معماری را در یک جمله: **مونولیت ماژولار** — یک استقرار Django، نه سرویس‌های ریز، با ۹ ماژول
مستقل (`accounts, projects, tickets, workflows, comments, attachments, notifications, audit, reports`)
که هر کدام model/service/selector/API/test خودش را دارد.

## ۲. ورود و داشبورد (۱ دقیقه)

1. لاگین با `manager@example.com` / `Demo!Passw0rd`.
2. اشاره کن به داشبورد: total / open / resolved / blocked، و جدول per-project.
3. **نکته‌ی مهم برای استاد:** «همه‌ی این اعداد در SQL و **با scope مجوز** حساب می‌شوند؛ یک کاربر
   فقط آمار پروژه‌هایی را می‌بیند که عضو آن‌هاست. برای همین در گزارش‌ها هرگز داده‌ی پروژه‌ی دیگر
   لو نمی‌رود.»

## ۳. یک بلیت، از اول تا آخر (۴ دقیقه) — قلب دمو

1. **Tickets → New ticket**: عنوان، توضیح، type=BUG، priority=CRITICAL، severity=MAJOR، کامپوننت.
   - بعد از ثبت: «کلید `ENG-N` **سمت سرور** ساخته شد، نه سمت کلاینت. اگر دو کاربر هم‌زمان بلیت
     بسازند، دو کلید یکسان نمی‌گیرند: یک counter per-project با قفل ردیف + unique index + retry.»
2. **صفحه‌ی بلیت**:
   - دکمه‌های وضعیت را نشان بده و بگو: «این دکمه‌ها hard-code نشده‌اند؛ از
     `GET /workflows/transitions/` می‌آیند. یعنی UI نمی‌تواند دکمه‌ای نشان دهد که بک‌اند رد کند.»
   - **TRIAGED** را بزن. بعد **IN_PROGRESS** را امتحان کن → خطای `assignee_required` با پیام
     روشن. «قاعده: کار بدون مسئول شروع نمی‌شود.»
3. **Assign** به `Eve Engineer`. بعد در تب دیگر (یا همان‌جا) **Notifications** را باز کن:
   اعلان فارسی/انگلیسی برای assignee ساخته شد.
   - «اعلان در همان تراکنش ساخته می‌شود، ولی ارسالش async است با Celery روی Redis؛ و `dedup_key`
     یکتا جلوی تکرار را می‌گیرد.»
4. **Comment** بگذار و یک **attachment** آپلود کن (یک فایل `.txt`).
   - «فایل با نام تصادفی در S3 ذخیره می‌شود؛ URL عمومی ندارد. دانلود از اندپوینتی می‌گذرد که
     مجوز را دوباره چک می‌کند.»
   - برای نمایش قدرت: یک فایل `.svg` آپلود کن → `dangerous_file_type` (جلوگیری از XSS ذخیره‌شده).
5. **IN_REVIEW → RESOLVED → CLOSED** (با کامنت جایی که لازم است).
6. **History** پایین صفحه: کل مسیر با actor و زمان. «این تایم‌لاین append-only است و در همان
   تراکنش با تغییر وضعیت نوشته می‌شود؛ پس هیچ‌وقت با وضعیت فعلی ناسازگار نمی‌شود.»

## ۴. کنترل دسترسی (۲ دقیقه) — نمره‌ی اصلی «صحت»

1. **Logout** و ورود با `reporter@example.com` / `Demo!Passw0rd` (نقش REPORTER در پروژه).
2. همان بلیت را باز کن: دکمه‌های وضعیت **کمتر** است (reporters می‌توانند reopen کنند، نه close).
3. تلاش کن بلیت پروژه‌ی دیگر را باز کنی (اگر وجود دارد) یا از API:
   - در تب دوم: `GET /api/v1/tickets/<uuid پروژه دیگر>/` → **404** نه ۴۰۳.
   - بگو: «برای عضو نبودن، ۴۰۴ برمی‌گردانیم تا وجود شیء هم لو نرود.»
4. با `admin@example.com` وارد شو → **Audit** را نشان بده: چه کسی، چه کاری، از چه IP، چه زمانی.
   - «جدول audit فقط append است: در پایتون `save/delete` استثنا می‌دهد و در production هم
     privilege دیتابیس revoke می‌شود.»

## ۵. اعلان، گزارش، تیم (۱.۵ دقیقه)

1. **Team**: اعضای پروژه و نقش‌ها؛ افزودن عضو از directory (فقط مدیر/PM).
2. **Reports**: workload هر مهندس + recent activity.
3. **Notifications**: unread count و mark-all-read.
4. اگر خواستی: `docker compose logs worker --tail 20` و خط
   `Task apps.notifications.tasks.send_notification ... succeeded` را نشان بده — «worker یک
   process جدا از API است؛ یعنی واقعاً async است.»

## ۶. کد و تست‌ها (۲ دقیقه) — «کد نویسی»

در ترمینال (فونت بزرگ):

```powershell
cd backend
.venv\Scripts\python -m pytest -q
# 237 passed, 1 skipped  (skip = تست همزمانی که فقط روی PostgreSQL اجرا می‌شود)

.venv\Scripts\python -m pytest apps/workflows -q      # ماتریس کامل گردش‌کار
.venv\Scripts\python -m pytest -m postgres -q         # اگر PostgreSQL دارید: 238 passed, 0 skipped
```

بعد یک فایل کلیدی را باز کن (نه همه‌ی کد):

- `apps/workflows/state_machine.py` — «جدول گذارها **داده** است، نه if/else؛ همین باعث می‌شود
  تست ماتریسی بتواند همه‌ی ۱۹ حرکت مجاز و ۷۱ حرکت غیرمجاز را بسنجد.»
- `apps/projects/permissions.py` — «همه‌ی تصمیم‌های مجوز در یک فایل، به‌صورت تابع خالص؛ هم API و هم
  service از همین استفاده می‌کنند.»
- `apps/tickets/services/keys.py` — «تخصیص کلید اتمیک: قفل ردیف + unique index + savepoint retry.»
- `apps/attachments/services.py` — «فایل خصوصی است؛ دانلود فقط از اندپوینت مجوزدار.»

## ۷. اگر چیزی خراب شد (نقشه‌ی نجات)

| مشکل | کار |
| --- | --- |
| داکر بالا نمی‌آید | `demo_up.ps1 -LocalOnly` (Django+Vite بدون داکر) |
| پورت اشغال است | اسکریپت خودش پورت آزاد انتخاب می‌کند؛ دستی: `NGINX_PORT` در `.env` را عوض کن |
| UI بالا نمی‌آید | فقط API را نشان بده: `http://localhost:<PORT>/api/docs/` و همان درخواست‌ها را از Swagger اجرا کن |
| داده به‌هم ریخته | `docker compose down -v` و دوباره `demo_up.ps1 -Reseed` |
| اینترنت قطع است | هیچ‌کدام از این‌ها به اینترنت نیاز ندارد |

**همیشه یک چیز آماده داشته باش که شکست نمی‌خورد:** خروجی `pytest -q` و لینک ریپو + badge سبز CI.
حتی اگر دمو خراب شود، «تست‌ها و CI سبز است» یک مدرک عینی از صحت است.

## ۸. جملات کلیدی که ارزش نمره دارند

- «منطق تجاری در view یا serializer نیست؛ در service است — یعنی از طریق admin، دستور مدیریتی و
  تست هم همان قواعد اجرا می‌شوند.»
- «وضعیت بلیت فقط از یک مسیر عوض می‌شود (transition endpoint)؛ نوشتن مستقیم `status` خطا می‌دهد.»
- «مجوز = نقش سیستمی × عضویت پروژه؛ هر دو لازم است.»
- «هر تغییری که روی داده اثر می‌گذارد، در همان تراکنش یک audit event دارد.»
- «هر چه تست نشده، در مستندات صریح نوشته شده که تست نشده — مثلاً رندر مرورگر.»
